# 项目开发指南

## 前端架构、设计取舍与面试介绍（2026-10-30 核对）

### 实际技术栈与文件职责

- 前端采用 Vue 3 全局构建版与 Composition API，使用原生 JavaScript、HTML 和 CSS；`web/index.html` 直接加载本地 `web/vendor/vue.global.prod.js`，由 `createApp().mount('#app')` 挂载。当前没有 Vite/Webpack 构建流程、Vue 单文件组件、TypeScript、Vue Router 或 Pinia，也未引入 Element UI 组件库。与编辑器统一的是视觉色板，不能据此描述为助手使用了 Element UI。
- `agent_1/airong_agent_test1/web/index.html` 负责模板与页面结构；`web/app.js` 负责响应式状态、交互、HTTP/SSE、会话存储和轻量 Markdown 渲染；`web/styles.css` 负责布局、响应式和品牌样式；`web/assets/company-logo.svg` 为用户提供的公司 Logo；`web/vendor/` 保存本地依赖。
- 前后端按职责分离、同源提供助手页面与 API：`backend/main.py` 使用 FastAPI 提供 `/api/*`，最后通过 `StaticFiles(directory=WEB_DIR, html=True)` 托管前端。浏览器不直接访问模型、BOM 数据库或 MySQL；这些能力由后端 LangGraph 运行层与只读工具完成。
- 选择零构建方案是沿用现有轻量前端，降低本机部署与依赖管理成本。本地 Vue 与 SVG 无需外部 CDN，但模型、数据库和编辑器功能仍依赖对应服务。当前交互集中在一个 Vue 根应用中，不能描述为已经完成大型组件化或微前端改造；业务规模扩大后的组件拆分属于后续设计。

### 页面布局、状态与交互链路

- 页面采用顶部品牌与工作区导航、左侧会话列表、右侧聊天内容及底部输入区的布局。Flex 布局与 `min-height: 0` 控制可滚动区域；CSS 媒体查询在窄屏将会话列表切换为抽屉与遮罩，调整顶栏和编辑器工具栏。
- 使用 `ref`、`reactive` 保存当前会话、草稿、附件、运行状态和工作区，使用 `computed` 派生消息与会话列表；`watch` 及页面生命周期事件参与状态同步和保存。浏览器 `localStorage` 保存消息、草稿和当前会话标识；后端检查点负责模型运行上下文，两者职责不同。待发送附件不持久化。
- 原生 `fetch` 发送提问、上传、停止等 HTTP 请求，`FormData` 上传附件，由后端提取文本；原生 `EventSource` 订阅 `/api/events?sid=...` 接收 SSE 事件。该设计适合浏览器发出请求、服务端持续推送生成进度与答复的交互。
- 一次提问的公开进度与工具事实集中显示在同一助手气泡的折叠过程区，最终答复独立显示，区分任务执行中、失败、取消和定稿状态。不能将公开进度称为完整内部推理。
- Markdown 使用项目自带轻量渲染器：先转义原文，再生成允许的标签，链接协议限制为 HTTP/HTTPS。它服务于规则代码块、列表和表格展示，不是引入完整 Markdown 编辑器或通用 HTML 富文本渲染。

### 编辑器整合与视觉设计

- 助手通常运行于8712，编辑器运行于8009。使用 iframe 嵌入现有编辑器，顶栏通过 `activeView` 切换工作区，无需路由跳转。`editorOpened` 初始为 false，首次打开才挂载 iframe；之后通过 `v-show` 隐藏工作区而保留 DOM，避免每次切换重建编辑器页面，并保持聊天连接、草稿和运行状态。
- 两个端口属于不同源。当前没有跨源 DOM 操作、单点登录或 postMessage 自动填充协议；编辑器使用自身登录。定稿消息按钮通过 Clipboard API 复制完整原始答复，然后切换编辑器，由用户粘贴所需规则并验证。复制失败提示手动复制，工具栏提供独立窗口链接。不能描述为已实现自动导入、自动验证、自动保存或发布规则。

- 视觉设计依据8009实际页面：深蓝顶栏 `#15315F`、主按钮蓝 `#0079FF`、灰底 `#f0f2f5` 与白色面板，使用 CSS 自定义属性统一颜色；公司 SVG Logo 放在助手名称前，白色衬底保证蓝色 Logo 在深色顶栏上清晰。按钮、边框与圆角向编辑器风格靠拢，并保留状态颜色与键盘焦点提示。

## 4. 业务工具与数据

### bom_search

- 当前适配层：`tools/bridge.py → tools/runtime-tools.mjs`，LangGraph 与 MCP 共用；`.pi/extensions/rule-search.ts` 保留为 Pi 回退适配。
- 实现：`tools/bom-search.mjs`，不依赖 Pi，可单独调用。
- 当前默认库：`bom/bom_非车.sqlite`；当前工具桥及 Pi 扩展均支持用 `BOM_SQLITE_PATH` 覆盖。
- 使用 `node:sqlite` 只读连接，延迟加载并在进程内缓存。
- 在线查询使用参数化 `LIKE`，匹配 label、field、fieldPath、className、codeService、searchText。
- 排序优先名称完全一致、前缀、包含，再考虑英文字段、类名及层级等。
- 默认 10 条，最多 50 条；方法节点默认排除，通过 `includeMethods` 启用。
- 通过祖先链构造 `qualifiedName`，用于区分不同对象下的同名字段。不要丢弃层级信息后直接选择首条。

`tools/bom-to-sqlite.mjs` 将 BOM 树展平，生成 `fields`、`params`、`classes`、`code_services`、`meta` 及可选 FTS 表。其管理用 search 子命令与在线 `bom_search` 的查询路径不同。`fts-text.mjs` 有中文二元分词辅助实现，但当前在线检索未引用它，不要描述为已启用。

### rule_search

- 实现：`tools/rule-search.mjs`，使用 `mysql2/promise`。
- 配置路径：业务目录 `config/mysql.json`，后续已使用该本地配置成功查询，连接前仍需重新检查可用性；部分字段支持 `RULE_MYSQL_*`、`RULE_BOM_BASE_INFO_ID` 覆盖。
- 当前实现仍先要求配置文件存在，不能假设仅设置环境变量即可运行。
- 范围链路：`decision_repository → decision_rep_catalogue → catalogue_rule_rel → rule_defined`，以 `BOM_BASE_INFO_ID` 圈定。
- 预定义来自 `rule_defined_predefine`；动作和参数来自 `rule_method_define`、`rule_method`、`rule_method_define_param`。
- 空格分词，词间 AND；每词在规则名、如果原文或预定义任一位置出现即可。“那么/否则”不参与关键词召回。
- SQL 加权粗排后在 JavaScript 精排，候选最多 150 条。核心默认展示 6 条，上限 30 条，可由配置调整；当前 Python Schema 默认 6、最大 30，Pi 回退 Schema 仍存在旧描述差异。
- 只为展示规则补动作；按分支和执行顺序排列，由代码完成方法占位符填参，不让模型二次拼装。
- 参数化查询、关闭多语句、连接池最多 2 个连接；瞬时故障默认最多尝试 3 次，指数退避并加入抖动。
- 查询含固定 15000ms 的 MySQL 执行时间 hint；不要把 README 中的 `statementTimeoutMs` 当作已接线的配置。
- 当前工具发出只读查询；数据库侧仍应使用正确授权的只读账号。

工具统一返回模型可读 `content`、结构化 `details` 和可选 `isError`。当前 Node 适配仅传播友好文案与错误种类，不将原始连接诊断传给模型；MCP 使用标准 `CallToolResult` 错误标记。技术诊断不得泄露凭据。

### BOM、关系表与规则 JSON 的核实记录

以下为此前对话中 MySQL 只读查询、本地 BOM JSON 和 SQLite 核对的历史快照；本次文档更新未重新连接数据库，不保证记录持续不变。

- SQLite 是嵌入式关系数据库，程序直接打开本地文件，无需独立数据库服务器。本项目用它保存 BOM 定义和层级索引，不保存每张保单的实际业务值，也不负责执行规则。`fields` 通过 `parent_field_id` 保留父子关系，`params` 保存 BOM 方法入参定义，`classes`、`code_services` 是聚合检索信息，`meta` 保存元数据。
- MySQL 保存已有规则及组织关系。`bom_base_info` 保存模型基本信息，`bom_model` 保存模型实现记录；`BOM_BASE_INFO_ID` 与 `BOM_MODEL_ID` 不可混用。`decision_repository` 同时引用两者。
- 规则归属链路为 `decision_repository → decision_rep_catalogue → catalogue_rule_rel → rule_defined`。目录与规则经关联表挂载，查询需去重，不能假设规则仅属于一个目录。目录表使用 `CATALOGUE` 路径而非父目录 ID；注释写英文点分隔，但实查样例为 `例外规则/企财险/01_通则`，解析前核实实际格式。
- `rule_defined.RULE_DEFINED_ID` 是记录主键；当前检索主要通过业务编号 `RULE_ID` 关联目录、预定义和动作。这些是字段关联及代码使用关系，不代表已确认数据库声明了相应外键。
- 四段式内容分开保存：预定义文本/JSON 在 `rule_defined_predefine.RULE_PREDEFINE_DESC/RULE_PREDEFINE_CONTENT`；如果文本/条件树在 `rule_defined.RULE_DESC/rule_content`；那么/否则动作在 `rule_method_define`，其中 `SETTING_THEN='1'/'0'` 区分分支，`ORDER_BY` 为字符串但按数值排序。不要把 `rule_content` 当作包含完整四段内容的 JSON。
- `rule_method` 保存方法模板，`METHOD_DETAILS` 定义输入槽位；`rule_method_define` 保存某条规则的一次动作配置；`rule_method_define_param` 经 `RULE_METHOD_DEFINE_ID` 保存该动作实际参数。SQLite 的 `params` 是方法定义，不能与此参数实例表混同。方法模板需考虑 `BOM_MODEL_ID` 版本，不能只按 `METHOD_ID` 裸连接造成行放大。
- 条件树常见节点为 `LOGICAL`、`COMPARISON`、`FIELD`、`CUSTOM`、`EXPRESSION`、`METHOD`。`left/right` 为子树，`code` 为比较编码，`returnType` 声明结果类型；`paramValue` 在常量节点是值，在方法/表达式节点可为参数节点映射。数字可能以字符串保存，须结合类型处理；业务代码应保留前导零。
- `fieldPath` 是业务引用路径；条件树中的 `path` 可能是 `.right.left` 等编辑位置，而 BOM 原始节点的 `path` 是带模型前缀的路径。同名键跨 JSON 结构不能套用同一语义。`fieldId` 不保证跨版本或预定义变量映射后相同，应结合来源、路径、类和类型核对。
- 预定义 JSON 样例使用 `specifyName` 定义变量别名、`variateName` 描述对象类型；`directedContent` 实际可为需再次解析的 JSON 字符串，其中 `nodePath` 指向来源列表。其 `leftNode/rightNode` 不等同于条件树字段。列表绑定的遍历次数和动作触发次数尚未通过原规则引擎确认。
- 动作参数的 `PARAM_TYPE` 是值类型，`PARAM_VALUE` 是可读表达文本；`EXECUTION_CONTENT` 样例用 `dataType='FIELD'` 表示引用、`'STRING'` 表示常量，`dataValue` 保存路径或值；`FIELD_PARSING` 保存 `${...}` 引用或带引号的常量表达。当前助手只还原展示，不执行这些表达式。
- `rule_expression_defined` 实查存在 `BOOLEAN_BELONG_TO` 和 `trueOrFalseService`；本次未查到 `GT/GE/STR_EQ` 记录，它们在样例中是 `COMPARISON.code`，不能假设所有运算符都在表达式表中。空元数据及 `afield` 等内部标记的完整语义尚未确认，不凭名称猜测。

真实参考样例：`YA_035243`（高保额设备业务管控规则），所属决策库 `YAIC_PROPERTY_UW_ExceptRules`，目录 `例外规则/企财险/01_通则`，模型基本信息名称 `YAICNonVehicleBom_202502271109`、版本 `v49`。

- 预定义“当前险别”来自 `appbase.productPropertyInfo01.coverage010006List`；条件为险别代码 `011301` 且保险金额大于等于 `5000000`。BOM 中金额字段为 `namt: double`，预定义引用路径为 `规则预定义变量.当前险别.namt`。
- 那么动作调用 `ResultXom_addUnderwriteRuleInfo_7`，三个参数依次为人工核保总公司二级、当前规则名称、固定提示“高保额设备业务，总公司核保。”；本次未查到否则动作。模板第二槽位提示为“规则编号”，实配却引用当前规则名称，不能擅自替换为规则编号。
- 本次发现该决策库引用的模型 ID 在 `bom_model` 中无对应行，`bom_model_detail`、`bom_field_method` 当时均为空表。不得因表结构存在就声称模型数据完整；当前字段查询依赖本地 BOM，动作还原依赖现存 `rule_method` 等记录。不因这些发现自动补库或重建。

## 6. 网页协议、会话与恢复

当前 API 在 `backend/main.py`，保持原 Vue 客户端所需协议：

| 接口 | 当前用途 |
| --- | --- |
| `GET /api/health` | 运行层、工具、Node 路径、检查点准备和会话状态；不证明模型/数据库健康 |
| `POST /api/prompt` | `{sid, message}` 接受本轮消息并创建异步任务 |
| `POST /api/abort` | 取消图任务、模型流和会话工具子进程 |
| `POST /api/new_session` | 停止当前任务并为 sid 更换 thread_id |
| `POST /api/close` | 释放内存会话和工具进程，保留持久化记录 |
| `GET /api/events?sid=...` | SSE 订阅 |
| `POST /api/upload` | multipart 单文件文本提取 |

- prompt 成功只代表接受任务，不代表模型回答成功。异常和取消也必须产生结束事件，避免前端一直 busy；同 sid 正在执行时重复发送会被拒绝。
- 前端继续消费 `message_update` 文本/思考增量、`message_end` 定稿、工具开始/结束及 `agent_settled`。事件形状兼容旧 Pi 不代表后端仍在运行 Pi RPC。
- SSE 每订阅者队列 2000，满时丢最旧事件，20 秒心跳；没有事件 ID 与可靠补发。打开页面会创建内存会话，但 Node 工具进程只在实际检索时启动。
- 最多 10 个内存会话，容量不足只淘汰无订阅且未运行的 LRU 会话；全不可淘汰则拒绝新增。每 60 秒检查，空闲超过 30 分钟且无订阅、未运行才回收。前端切换生成中的会话仍会请求停止。

当前存储分层：

1. 浏览器 localStorage：页面消息、标题、草稿、sid，最多 50 个会话、每会话最近 300 条。
2. Python 内存：sid → Session，任务、锁、订阅者与工具桥。管理器属性 `bridges` 为兼容已有 API 命名，不代表 PiBridge。
3. `config/langgraph/sessions.sqlite`：sid → thread_id；`config/langgraph/checkpoints.sqlite`：图消息、工具结果、摘要和检查点。与 BOM SQLite、业务 MySQL 分开。

关闭后相同 sid 可恢复模型历史；新会话更换 thread_id，不删旧检查点。取消/失败/崩溃后下一轮保留最近完整对话，不将未完成工具轮次带入，也不会自动继续未完成生成。首次旧 sid 可只读导入 `config/pi-agent/sessions` 当前分支的用户/助手消息、工具调用和工具文本结果；原文件保留，LangGraph 后续对话不会自动回写 Pi JSONL。不同持久化格式、所有旧分支和产品功能不能宣称完全等价。

上下文按配置容量和输出预留估算预算，超出时对早期消息分块摘要，保留完整磁盘记录和最近完整轮次。摘要有模型误差，精确规则应重新检索；单轮输入过长或摘要失败会明确报错，不能宣称全文已处理。浏览器历史与模型历史仍不是同一个数据源，没有完整双向同步。

当前为本机、单进程单 worker。没有完整认证、会话归属、共享运行注册、SSE 补发或多实例协调。扩容或对外部署必须另行设计路由、隔离和取消传播。旧 Pi 的命令 id/Future、60 秒 RPC 应答和 TUI 自动取消仅属于 `legacy/pi/`；当前工具桥的 60 秒响应超时也不是完整生成时长限制。

## 7. 附件处理

- `/api/upload` 在内存提取文本，前端再将文本块拼入 `/api/prompt` 消息。
- 支持文本/代码类、PDF、DOCX；单文件最大 20MB，提取文本最多 30000 字符，超出截断。

### 两项核心业务需求

**已有规则检索**：从用户自然语言中提取关键词、业务对象和限定条件，到公司已有数据库查找相关规则，提取完整规则并按公司要求展示。

- 模型负责理解意图、提取检索条件；必要时调整关键词或澄清歧义。
- 数据库规则内容尽量由代码还原和格式化，完整保留预定义、条件、动作和例外分支，避免模型自由改写已有规则。
- 不把候选数当作精确总数，不因无结果就编造规则，不跨业务范围擅自查询。

**文档规则提取与规范化**：用户上传新的业务文档，系统提取其中的新规则，并转换成公司规定的规则格式。

- 先识别条款中的适用范围、条件、阈值、动作、例外与生效条件，再映射公司 BOM 字段、方法和运算符。
- 保留每条候选规则的原文依据和可获得的位置，例如页码、章节或段落；提取结果与推导内容应能区分。
- 检查重复、冲突、信息缺失及无法映射的术语；不猜测补齐业务口径。
- 字段存在性、运算符类型匹配、方法参数等可确定规则优先由代码校验，不能仅依赖另一个模型审查。
- 当前上传仅为文本内联，尚不等同于完整文档规则提取流程。需处理长文档分段、跨段汇总及覆盖检查，不能静默截断后宣称全部规则已提取。
- 公司最终交付格式尚待样例明确：现有四段式文本可作为当前基线，不能默认公司还要求可导入的 JSON/DSL。实现前以认可的输入文档、目标输出样例确定格式和验收标准。

未来可能扩展其他 AI 功能，但具体范围尚未确定。文档对比、影响分析、多 Agent、OCR、知识库、测试用例生成等均为可选方向，不是已承诺功能，不应提前全部建设。

### Redis 与其他按需基础设施

- 本机单进程功能等价迁移不要求 Redis：运行注册、会话锁和事件队列可先使用进程内机制，持久化使用数据库。
- 多 worker/多实例时，可评估 Redis 用于运行归属协调、带租约的锁、取消通知、事件分发、共享缓存和统一限流。必须设计过期、故障恢复和会话路由；安装 Redis 不等于实现恢复或可靠取消。
- Redis Pub/Sub 不提供可靠历史补发。若需要 SSE 断线补发，需设计事件 ID、保留和重放，可评估 Streams 或数据库事件表；这不是现有功能已具备的保证。
- 长文档确需后台排队、脱离 HTTP 进程执行时，再选择 Celery 等任务队列；原文档保存和导出需求明确后再评估内网对象存储；扫描件需求明确后再评估 OCR。
- pgvector、Qdrant 等向量检索只在语义检索需求和样例评测支持时引入，不能取代现有精确规则查询，也不因框架迁移默认建设。
- 多人内网部署须增加身份认证、会话归属及业务范围隔离，按环境配置反向代理、进程管理、备份和日志；可逐步增加 OpenTelemetry，不强制公网追踪服务。
- 建议分两阶段：先完成单机功能等价迁移及新旧样例对照；再按实际并发和业务需求增加 PostgreSQL、Redis、认证或后台任务。上述可选组件均不构成自动安装或部署授权。

### 性能测量口径与步骤

- 分三层测试：工具组件（BOM/MySQL及JSONL桥接）、单次私有模型请求、完整 HTTP/SSE Agent 任务。优先关注最终答案首正文时间、任务总耗时P95、失败率和质量/时延均达标的有效吞吐。
- 模型 TTFT 是单次模型请求发出至首个非空输出；思考、正文和工具调用首输出分列。应用首可见正文是发送 prompt 至首个非空 `text_delta`，不计心跳、思考、HTTP200或工具状态。
- 最终答案首正文时间是发送 prompt 至最终无工具调用的助手消息开始输出；需按模型请求/消息归属记录delta，待 `message_end` 确认后回填，不能把“正在查询”当最终答案。
- 任务E2E是发送 prompt 至本轮 `agent_settled`，区分成功、错误和取消；HTTP接受任务不等于成功回答。先建立SSE订阅并确认就绪再发prompt，断流计测量失败。使用客户端单调时钟，不混合不同机器墙钟相减。
- 工具耗时按 `toolCallId` 配对开始/结束，分BOM/MySQL、冷启动/复用统计P50/P95和错误。核心 `elapsedMs` 不包含全部启动与桥接开销。
- 输出速度/TPOT依赖真实Token数或一致tokenizer；相邻SSE正文分片间隔只能称流式分片间隔，不冒充精确Token间隔。单次模型TPOT不能用包含工具等待的完整Agent总耗时直接计算。
- 记录每任务模型/工具次数、输入/输出/思考Token、可获得的CPU/RSS、GPU显存和排队信息；摘要请求也计入，未采集项明确标记。另报成功任务吞吐及质量和预定时延SLO均达标的goodput，失败/超时/拒绝不得从分母剔除。
- 冻结数据、模型、提示词、Skills、输入/输出长度和推理配置。先每例顺序重复3次观察波动，再以不同sid测试并发1、2、4、8；冷热分开，正式每档建议至少100次记录，报告P50/P95和样本数。需要找饱和点时再补固定到达率测试，不能无上限施压。
- 当前最多10个内存会话；容量拒绝属于应用限制，不能一概归因模型。使用隔离评测存储，避免污染用户历史；冷启动测试使用独立测试进程，不重启现有用户服务或清理数据库WAL。
- 当前已有文本、思考、工具、定稿与收尾事件，但没有完整性能采集器、自动批量模型运行器或语义评分器；严格Token级统计还需模型适配/服务端配合。详细定义、公式和官方资料链接见 [评测说明](agent_1/airong_agent_test1/evals/README.md)。

### 指标定义与计算口径

| 指标 | 定义及使用条件 |
| --- | --- |
| Recall@K | 前 K 条中找到的不同相关规则数 / 标注的相关规则总数；需足够完整的相关集合 |
| Precision@K | 前 K 条中不同相关规则数 / 实际返回的不同规则数（最多 K）；采用此口径时明确实际分母，不与固定 K 分母混报 |
| 目标规则命中率@K | 前 K 条包含经核实目标规则的案例数 / 有明确目标的案例数 |
| 关键要素正确率 | 正确要素数 / 被检查要素总数；拆分对象、字段、值、单位、比较符、逻辑、例外和动作 |
| 案例通过率 | 满足全部必需条件且未触发禁止项的案例数 / 适用案例总数 |
| 文档规则召回率 | 正确匹配到的标注规则数 / 应提取规则总数 |
| 文档规则精确率 | 正确匹配的输出规则数 / 系统输出规则总数 |
| 运行与权限 | 正常结束率、错误率、取消成功率、越权请求拦截率，以及实际发生未授权执行的次数 |
| 性能与资源 | 首个可见文本耗时、完整耗时 P50/P95，以及每任务模型请求、工具调用、Token；不可获取项标为未采集 |

- 检索指标分别统计工具候选与最终展示结果，区分“检索没找到”和“找到但模型漏写”。仅知道一条目标规则时可评命中率，不能声称测得完整召回率；工具返回的候选数也不是数据库相关规则精确总数。
- 例如 4 条标注相关规则中，前 5 条结果找回 3 条，则 Recall@5 为 3/4；返回 5 条时 Precision@5 为 3/5。先去重，明确每例计算、跨例平均和失败/超时处理方式，不能剔除失败案例使成绩虚高。
- 无相关规则、无返回结果、分母为零的情形预先定义，通常单列无结果处理与澄清指标，不与普通召回率混算。
- 关键阈值错误时，即使其余 9/10 个要素正确，案例仍失败。既报告要素正确率，也报告整例通过率和关键错误，不能只报总分。
- 文档规则匹配须预先确定粒度、等价条件、一对一匹配、重复、合并/拆分及遗漏例外的处理，防止重复输出提高召回；同时检查来源、位置和关键业务要素。
- 性能需注明并发、环境、样本量与统计范围。报告失败和超时；质量达标后再比较速度与资源，不以少调用工具换取漏查。

### 评分方式

- 可确定的内容优先程序检查：目标规则/字段标识、工具 Schema、范围、分支、数值、结束事件、权限及耗时。语义尚未结构化时应明确自动检查的覆盖限制。
- 数值、比较符和例外不能仅靠关键词命中评分，例如否定句也可能含目标关键词。业务语义等价、复杂例外及表达是否清楚需由业务人员判断。
- 模型可辅助筛查或评分，但不单独作为高风险业务答案的最终裁判；关键金额、例外和动作参数应程序检查并按需人工复核。若使用模型评分，记录其版本、提示词和评分规则，并用人工样本校准。
- 可允许格式、缩进和非关键措辞差异，但不能放宽条件、逻辑、范围及动作语义。评分尺度须在评测前确定。

### 结构化规则与可信证据状态

建议在最终中文文本之前引入内部规则结构，并在图状态中显式保存：

- 来源：文件、标题/段落、原文片段及适用范围。
- 预定义：变量、来源列表、元素对象与绑定关系。
- 条件树：字段引用、运算符、常量、类型、单位及AND/OR/NOT关系，不能用无括号的散文替代逻辑结构。
- 动作：方法引用、类型明确的参数、分支和执行顺序。
- 例外、否则分支、待确认项与每条规则的处理状态。
- 宿主登记的字段/方法候选、实际工具返回证据、业务范围及模型/数据版本。

模型只能提交对候选的引用，宿主再从可信检索记录核实引用；不能把模型自行填写的路径、类型、证据或“已核实=true”当作事实。内部结构不必暴露给业务人员，最终四段式由程序统一渲染。

可使用Pydantic检查结构与参数，但当前是自定义Chat Completions模型适配器，需单独接入解析、校验与错误处理；不得假定已具备LangChain的结构化输出接口或服务端JSON Schema支持。结构合法仅表示形状正确，仍需业务与证据检查。

### 确定性校验：从检查格式扩展到检查内容

| 校验项 | 建议检查与拦截内容 |
| --- | --- |
| 字段与方法证据 | 所有引用均有实际检索依据；核对完整对象路径、模型版本及同名字段，不能只比标签 |
| 类型与运算符 | 文本、数字、日期、布尔、列表操作的兼容性；void方法不得用于条件；方法返回类型须匹配使用位置 |
| 常量、单位与边界 | 金额单位换算、日期开闭区间、比较符及代码前导零；用明确类型保存值 |

| 来源与覆盖 | 每条输出规则有真实来源；每个候选条款都有转换、背景、待确认或失败状态 |

`文档解析与分段 → 候选条款识别 → 字段/动作映射 → 结构化规则生成 → 程序校验 → 定向修正或业务澄清 → 四段式渲染`

- 各节点保存结果和失败原因；校验反馈采用具体错误清单，明确哪条规则、哪个引用或参数有问题。只修正失败规则，避免整篇文档反复生成。
- 限制修正次数，失败后保留已通过规则及待确认项，不无限循环；暂未核实的规则不能伪装成可用成品。
- 当前附件层会截断到30000字符；后续应在截断前保留标题、段落、表格表头/单元格关系，并按条款分批处理。原文已经丢失后，后续模型或校验不能恢复未读内容。
- 分段要携带适用范围、上级标题和跨段例外等必要上下文，不能独立切碎后丢失限定条件。每段维护“已转换、背景材料、待确认、处理失败”覆盖台账，检查遗漏与重复。
- 后续引入持久化文档或分段内容时，明确存储、隐私和清理策略；不要沿用“原附件不落盘”描述来掩盖新增持久化。

### 语义复核、边界测试与人工澄清

- 对照原文和结构化规则核对遗漏条件、新增动作、否定/例外及作用范围。可用独立模型辅助复核，但模型自评或两个模型一致都不是最终正确性证明；仍需证据校验及关键案例复核。
- 为金额、日期和逻辑条件构造边界测试，例如“达到500万元”检查低于、等于、高于阈值，验证等号及单位；原文预期应来自已审核标注，不能只让同一个生成器同时编规则和标准答案。
- 前期可测试受控的内部条件结构；不要执行任意模型生成代码。列表触发次数、方法副作用等仍需确认真实规则引擎语义；自建模拟器通过不能冒充原引擎执行或发布通过。
- 不确定的业务口径应暂停并询问用户，保留原文与候选选择，不能自动补阈值/核保级别。可评估LangGraph `interrupt` 与恢复机制，但需同步接入后端恢复API、检查点、前端交互和事件收尾；当前尚未具备该文档澄清流程。

### 性能治理与后续评测

- 在任务内缓存已确认的字段、方法及对应模型/数据版本；重复检索去重，不能跨业务范围或版本复用错误证据。
- 查询预算、重复调用限制和修正上限由程序执行，不能只依赖Skill提示。达到上限时明确待确认或失败，不能为了减少工具次数跳过必需核实。
- 按规则/段落处理并局部重试，独立任务仅在明确容量上限内并发；保持会话隔离与取消传播，不无上限对真实模型或业务库施压。
- 分别测文档解析、候选识别、映射检索、模型请求、校验、修正和渲染耗时；有条件再采集Token、排队及资源指标。不能仅凭总耗时断言模型推理或数据库就是瓶颈。
- 固定数据、模型、提示词与评分口径做前后对照；沿用第14节全量分母和截断说明，不把状态提示当首正文、不只报成功子集速度。
- 在现有召回率、来源语义精确率、完成率、超时率之外，重点增加“全部引用有据的整例通过率”、条件/动作语义保真与条款覆盖；指标需明确关键引用子集和全部引用的区别。
- 加入真实长文档、跨段例外、表格、多动作/否则及未见新需求；同时加入信息充足的可完成案例与确需澄清案例，检查过度拒绝/过度澄清，防止通过大量输出待确认获得表面低错误率。
- 具体验收门槛仍需业务方确定；增加机制或测试样本不自动代表已达到公司验收标准。

## 16. Skill链路、转换性能与剩余优化项（2026-10-27）

本节根据本轮代码阅读、会话只读诊断和用户反馈补充。前文10/14/16/19项回归为各阶段历史快照，最近一次代码回归为21项通过；本次仅更新文档，未新增代码、运行真实评测、重启或部署服务。用户已反馈通过带 `--app-dir` 的命令启动成功，但不能据此确认其当前进程始终加载最新代码、配置和全部改动。

### 当前Skill实现的准确边界

- 当前业务目录只有 `.pi/skills/rule-authoring/SKILL.md`。`config.system_prompt()`读取 `.pi/APPEND_SYSTEM.md`，按路径排序递归读取所有 `SKILL.md` 全文，再追加宿主工具约束；创建每次任务图时加载，不由模型调用read工具。普通问答、Web及CLI共用此机制。
- 目前不是按description匹配的渐进加载。frontmatter的name/description没有解析成技能注册或路由元数据，而是随全文交给模型；程序检查技能名称时使用目录名。增加技能会增加所有普通模型请求的提示内容，需核对上下文预算、内容冲突及加载开销。
- `/skill:rule-authoring ...`目前只检查技能目录是否存在，移除前缀后进入同一图；不会只加载指定技能，也没有独立技能执行器。空命令使用默认请求。后续如实现指定技能路由，须补齐任务类型选择，不能把当前命令描述成已具备隔离技能上下文。
- `authoring.py`用用户请求中的关键词识别转换任务，并追加DOCUMENT_PROMPT；不依靠Skill的description自动路由，只检查附件标记前的请求，避免附件内容自行决定任务。关键词路由仍可能漏判、误判，尚无完整任务分类和覆盖测试集。
- 技能规则通过模型影响工具调用和文本输出；工具执行在 `graph.py → tools/bridge.py → runtime-tools.mjs`。独立MCP仅暴露检索工具，不加载业务Skill、不执行转换图；外部MCP客户端不能被假定自动拥有本项目业务规范。
- Skill引用的其他资源不会自动注入。新规则的动作选择及文本组织仍主要由模型完成；已有规则动作由检索核心填参、宿主直接保真展示，两条路径不能混称为程序统一渲染新规则。
- Skill文件在后续任务创建时重新读取，正在运行的任务保留已有提示；Python模块修改需要重启进程加载。统一要求重启是操作上的稳妥建议，不代表Skill全文仅在服务启动时读取。

### 当前转换链路与已知性能问题

实际链路为：准备文本/恢复历史 → 加载提示与Skill → 必要时模型摘要旧历史 → 模型分析并生成工具请求 → 串行执行工具并将结果加入历史 → 再次请求模型 → 有限交付检查及必要的模型修正 → 最终正文和待确认项。并非每个业务步骤均已有独立的结构化节点。

| 问题 | 已确认现状 | 待优化方向 |
| --- | --- | --- |
| 模型往返过多 | 每次是否继续查询、换什么关键词主要由模型判断，工具结束后重新请求模型 | 先形成条件/动作映射清单，集中查询，程序记录哪些引用已确认或已耗尽尝试 |
| 结果与历史膨胀 | 工具返回的content及details一起序列化进入历史；完整规则、结构化详情可能重复，同轮结果不断累计 | 原始证据留宿主，模型侧提供必要片段及稳定引用；不得删除验证必需依据或破坏工具消息配对 |
| 检索串行 | 同一批调用由tool_node依次await，NodeTools也有会话锁及串行JSONL进程 | 核查依赖后评估有限并发/批量查询，同步响应匹配、取消传播、连接池及容量约束；仅加gather不能保证现有桥接安全并发 |
| 缓存覆盖有限 | 仅本任务中校验后完全相同的成功请求命中缓存，换关键词仍会实际查询 | 按字段/方法建立证据登记与查询状态；跨任务缓存需明确范围、版本及失效策略，不能直接全局复用 |
| 收敛缺少逐项控制 | 已有12轮普通模型节点及48次工具请求上限，但每字段两次关键词失败的约束主要依赖Skill | 程序按引用计数并停止无效重试；达到预算仍尽可能保留完整草稿和明确待确认项 |
| 摘要与修正附加请求 | 历史摘要和交付修正可产生普通模型节点计数之外的请求 | 为模型总请求数、阶段耗时及修正次数建立统一预算；不要宣称12轮等于最多12次HTTP请求 |
| 缺少任务总期限 | HTTP的180秒超时不是整项生成期限；工具桥60秒仅约束一次响应 | 增加任务/阶段截止时间、取消收尾及部分草稿交付策略，不仅依靠网络空闲超时 |
| 思考输出缺少独立治理 | 普通配置max_tokens为32768；没有独立、经实际模型协议验证的思考预算 | 先结合诊断确认耗时分布，再验证服务支持的生成控制；不能靠任意增加额度解决重复推理 |

本轮只读会话检查中，有与用户截图相同的输入约470字符；一份记录在0轮、无工具结果时失败，另有同类记录消息JSON约23.7万字符，其中工具消息约19.6万字符。两种现象应分别分析，不能将所有截断归因于历史过长，也不能将字符数当token数。该快照不是最新修改后的性能评测。

第14节历史评测BOM查询P50为20.6ms、规则查询P50为1.183s，多数时间发生在多轮模型请求阶段；这支持优先排查模型往返和上下文使用，但未拆分GPU推理、排队及输入处理，不能确认某项服务端瓶颈。新增缓存、折叠过程及日志后未做同口径真实前后对照，不报告性能提升百分比。

### 正确性与完整交付的待优化项

- 目前没有完整规则IR及逐引用可信证据台账，Skill写明“字段来自BOM”不等于程序逐字段核验。需核对对象归属、类型、方法返回值及参数数量/顺序、枚举、单位、前导零、AND/OR/NOT与例外范围。
- 当前delivery_issues主要检查代码块、如果/那么、全篇是否有来源字样，以及成功工具调用存在性或待确认说明；一次工具成功不证明全部字段已查实，全文含来源不证明每条规则有真实定位，全文含待确认也不证明缺失依据均已列明。
- “未识别到可转写规则”的文本分支仍依赖模型判断，尚无覆盖台账证明原文确实没有规则。需防止模型用该表述绕过交付，也需允许真正的背景材料正常结束。
- 部分字段/动作待确认时，用户明确要求先交完整草稿，再在结尾逐项说明；不能通过拒绝输出、删去条件或只输出确认清单来规避错误。草稿中保留的用户中文原文不能冒充已存在BOM字段或已核实方法。
- 现有一次交付修正失败仍会整体报错；长度截断保留了浏览器过程，但不等于恢复了完整规则。应设计保留已通过条款、局部修正及明确标记不完整草稿的机制，不执行半截工具调用，不把未完成文本当合格成品。
- 新规则动作缺少可信模板的统一程序渲染及参数验证；不要将已有规则的代码填参能力泛化为新规则已具备该能力。
- 长文档仍缺结构保留、跨段限定及覆盖台账，原文截断后的内容不能由模型恢复；相关设计继续按第15节推进。

### 可观察性、启动与验证边界

- 转换过程已折叠展示，截断/失败后保留已接收文字；只能观察服务实际返回内容，不能还原全部内部推理，也不能据此证明推理正确。过程随浏览器消息保存，较长文本可能增加localStorage与页面开销，应评估容量、保存频率及显示策略。
- model_diagnostic/task_metric已有请求、字符数、耗时及可选usage诊断，默认输出终端。没有自动持久指标平台，没有模型首token、服务端排队/输入处理/生成的完整拆分；usage未返回时仍无法得知真实token消耗，不保证截断后还有最终用量包可读。
- finishReason=length只能确认服务报告长度截断，不证明一定用完客户端32768 tokens。应结合maxTokens、输入规模、正文/思考字符数、usage及模型部署机器日志；本地requestId不保证等同远端请求ID，responseId也需对照部署实际日志。
- 用户说明模型运行在本地服务器，但本轮未确认服务器操作系统、具体部署方式、服务版本、启动参数和日志配置，未登录该服务器。Docker/systemd命令是条件式指导，不能写成已查到容器、服务日志或GPU瓶颈。排查不打印密钥和业务全文。
- 启动脚本仍默认监听127.0.0.1，不能默认供其他电脑访问。用户已通过显式 `--host 0.0.0.0 --app-dir <业务根目录>` 启动成功；脚本尚无统一局域网绑定参数。后续可改善启动参数与日志入口，保留本机默认和端口冲突不杀进程行为。
- 用户曾从 `.venv-langgraph/Scripts` 目录启动导致backend.main导入失败；入口须固定业务根目录或显式app-dir，避免要求用户手动猜cwd。局域网连通仍需核对主机实际IP、端口、防火墙与网络隔离，不扩展为公网部署或权限隔离已完成。
- 后续验证应同时检查规则完整性、逐引用依据、草稿与待确认标记、实际完成率、总模型请求数、上下文大小、全样本耗时及截断率。模拟回归通过、网页能启动或看到过程，都不能替代真实业务质量和性能验收。

建议落实顺序：先用新诊断完成一次可复现的耗时定位，同时减少重复上下文；再建设映射/证据状态与逐项预算；随后接入结构化规则、确定性校验、可信渲染及长文档覆盖。此顺序是建议，不是本轮已授权实施全部方案；本次仅记录问题，不自动切换模型、修改数据库、扩大工具权限或部署。

## 17. 保留Skill的受控结构化转换方案（2026-10-27，待实现）

本节补充后续优化的具体设计，承接第15、16节。用户本轮要求更新文档，未要求立即实现整套方案；以下不是当前功能、性能承诺或业务验收结果。目标是同时降低模型往返及上下文规模，并提高完整交付与依据可核验性，不能以减少查询为由跳过必要核实。

### 推荐方向与方案选择

- 建议保留Skill中的业务规范，将可确定执行的检索调度、证据登记、预算、校验和排版迁入程序；模型主要负责原文理解、可信候选选择及难以程序判断的语义。不因现有问题再次更换框架，可在当前LangGraph业务层逐步扩展。
- 仅增加Skill文字可能改善部分输出，但不能强制每个字段有据，也不能可靠限制重复查询。增加多个模型/Agent互相审核可能增加耗时与上下文，一致意见不构成正确性证明，暂不作为性能治理的首选；本节不授权主动创建子智能体。
- 结构化输出只约束数据形状，不保证业务含义。程序可保证引用与已定义校验规则成立，但原文歧义、例外范围及未确认引擎语义仍需保留待确认或人工复核，不能承诺任意条款百分之百正确。

### 建议目标链路与状态

`原文结构化提取 → 程序去重并集中检索 → 从可信候选选择映射 → 程序校验 → 限次局部修正 → 程序渲染完整规则/草稿 → 结尾列待确认项及来源`

1. **先提取完整业务含义，再映射BOM。** 保存原文片段、真实来源位置、适用范围、预定义绑定、条件树、常量与单位、动作及分支顺序。AND/OR/NOT和括号需显式表达，业务编号/枚举代码保留字符串与前导零。提取阶段不提前猜BOM路径，不把参考规则阈值或动作当成原文事实。
2. **统一形成映射需求并查询。** 按字段、枚举、方法去重，集中安排检索。每项记录状态、已尝试关键词、次数、失败原因及候选；达到逐项上限后停止无效重试，保留原文业务描述。与总模型请求数、工具请求数和阶段时间预算共同约束。
3. **模型仅选择可信候选引用。** 宿主给候选分配稳定引用，登记完整对象路径、类型、方法模板/入参及业务范围和版本。模型可选择引用或声明无合适候选；路径、类型、证据及“已核实”状态不能由模型自行填写后直接采信。
4. **校验结果保存为结构化错误。** 标记哪条规则、哪个条件/动作、哪项证据或参数失败。已通过部分保留，只发送失败部分及必要上下文进行限次修正，不反复生成整条规则或整篇文档。
5. **最终文本由可信状态渲染。** 已确认引用使用BOM规范名称，未映射项保留用户中文业务原文。完整输出草稿及全部条件/动作/分支，末尾统一列待确认项，不冒充可执行成品。原文缺少动作要明确缺失，不自行补核保级别。不能以拒绝输出或大量待确认替代本可完成的转换。

普通短规则可将原文提取与候选映射设计为两个主要模型阶段，必要时增加局部修正；这是规划目标，不能硬性承诺所有任务两次模型请求内完成。长文档按条款处理，携带上级范围、跨段例外和覆盖台账，避免整篇反复发送。

### 上下文与耗时控制

| 当前问题 | 建议改造 | 必须保留的边界 |
| --- | --- | --- |
| 工具文本及details重复进入历史 | 原始结果留宿主，模型只收当前阶段必要候选、片段及引用 | 不删核实所需类型/归属信息，保留证据可追溯性 |
| 依赖完整聊天消息推进每一步 | 独立阶段输入明确结构化状态，历史只带本任务需要的背景 | 不悄悄丢掉用户补充、上级范围和例外 |
| 参考规则全文反复发送 | 只给相关动作模板或必要片段，已确认映射用引用复用 | 参考规则不是新文档事实依据；已有规则查询仍原样完整展示 |
| 模型想到一个字段查一个 | 去重后的需求集中检索，再统一选择候选 | 独立项才可有限并发，先改造现有串行桥的响应匹配/取消机制 |
| 修正导致整份内容再生成 | 按失败条件或动作局部修正，固定总请求和时间预算 | 不执行半截工具调用，不将截断文本当完整成果 |
| 全部技能/示例每次全文注入 | 按阶段提供简短规范与必要资源 | 须显式实现加载路由，不能假定现有description或引用文件已自动加载 |

精确阈值、比较符、否定、例外和动作参数应从保存的原始/结构化记录读取，不能只靠有损摘要。宿主新增持久证据或文档存储前需明确保存、清理及隐私策略；跨任务缓存需按范围、版本及失效条件隔离。

### 程序校验与结构化输出接入

- 引用校验：字段/方法属于宿主可信候选，完整父链、对象和业务范围正确；仅存在同名标签不算匹配。
- 类型与参数校验：常量、运算符及方法返回类型兼容，动作参数数量、顺序及类型符合可信模板；未知业务元数据不凭名称推断。
- 完整性校验：每个已提取条件/动作有映射或待确认状态，每个原文候选条款有处理记录。提取列表内部完整不代表原文未漏提，仍需来源对照与覆盖检查。
- 来源校验：引用片段确实存在于保存原文、位置真实。片段存在不证明模型解释正确，不能替代语义复核。
- 渲染校验：从结构化状态输出四段式，确保已保存分支和动作不因模型排版丢失；可信模板填参不能照搬模型自行编造模板。
- 可先沿用当前模型和自定义Chat Completions适配，定义Python/Pydantic结构，解析后校验，失败限次修正。当前代码没有自动获得LangChain `with_structured_output` 能力。
- 如部署版本及模型实际支持，可另行接入JSON Schema约束输出，验证与思考、工具调用、流式响应、截断及取消的兼容性。不直接照搬新版vLLM请求字段，不默认修改服务器参数或切换模型；格式合法不等于业务正确。

### Skill的配套精简建议

将规范按阶段组织为原文提取、候选映射、歧义处理、语义复核四类，每阶段只提供必要说明与经审核的正反例。运算符规则、方法模板、参数定义逐步由程序读取并执行；模型获得当前需要的部分。拆文件后必须同步实现宿主按阶段加载与上下文预算，不能只移动文件后假定模型仍能读取。

保留“完整草稿优先、末尾列待确认”“不捏造BOM或原文动作”“已有规则不改写”“来源可追溯”作为共同约束。提示词、Skill与程序校验规则更新应同步，避免重复或冲突；不能通过简化提示词放宽工具白名单和业务范围。

### 分阶段落地与验证口径

1. **低风险观测与上下文治理**：精简模型侧工具结果，保留宿主原始证据；记录各阶段模型调用数、输入规模与耗时；将重复查询管理迁入程序。
2. **受控转换主线**：引入条件树、动作、来源结构与映射状态；集中检索、候选选择、确定性校验、程序渲染及局部修正。保留现有普通问答、已有规则全文查询与会话取消恢复行为。
3. **复杂任务与服务优化**：补长文档覆盖、跨段例外及复杂动作，结合服务端数据决定生成参数与容量策略。未定位前不先加大输出额度、不默认更换模型或堆叠多Agent。

使用相同案例、范围、模型、评分口径比较改前改后：全量完成率、语义正确率、完整交付率、全部引用有据的整例通过率、待确认项准确性、条款覆盖、模型请求数、实际输入/输出token（服务有返回时）、截断率及全样本耗时。失败与超时纳入分母，不只报成功子集、不将字符数当token、不通过过度拒绝/过度待确认获取表面低错误率。新增机制通过模拟回归后，仍需真实模型及业务样例复测，不能承诺未经测量的提速比例。
