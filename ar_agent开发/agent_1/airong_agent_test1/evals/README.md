# 核保助手评测集与测量方案

本轮于 2026-10-23 只读连接现有配置的 MySQL，并读取本地 BOM SQLite，构建首版 32 条评测案例；未运行模型质量评测或压力测试。没有修改业务库、运行服务或模型配置。

## 文件与使用

- `private/dataset.jsonl`：32 条输入、任务、来源分组、参考要素与禁止项。
- `private/sources.json`：10 条规则的工具结构化结果、四段式展示参考，以及独立 SELECT 获取的条件原文/JSON、预定义、动作和参数快照。参考展示复用生产格式化函数，须与 raw 原文人工交叉核对，不能用同一函数自证正确。
- `private/review.md`：逐条可读审核表，包含输入和判分标准。
- `private/manifest.json`：时间、业务范围、数量、文件 SHA256、限制。
- `build-dataset.mjs`：复现只读采样。业务根目录执行 `node evals/build-dataset.mjs` 会重新访问数据库并覆盖本地当前版本；冻结版本前先复制整个 private 目录到公司批准的本地存储。
- `inspect-source.mjs`：定向查看前 600 条候选，排除名称含“测试”及编号含 TEST，只选 YA 前缀；它不是全库扫描。最终建集另按明确业务名称检索，来源以 manifest/sources 为准。

真实业务样本和报告通过本目录 `.gitignore` 排除，不默认提交或上传。审核表和标准答案仅供评测侧使用；发给模型的只有 input，不能携带 expected 或 sources。建集时尚无运行器；现已新增文末所述针对性运行器，复杂语义仍需逐项核对。

## 样本选择与局限

| 功能 | 数量 | 重点 |
| --- | ---: | --- |
| 已有规则检索 | 10 | 自然语言改写、明确目标、地区/渠道、相似方案 |
| 已有规则展示 | 6 | 预定义、条件、逻辑、阈值、动作填参保真 |
| BOM 映射 | 8 | 完整父链、同名字段、类型；保留同名候选供审核 |
| 规则编写 | 4 | 从数据库规则派生规范化任务，核对字段与条件动作 |
| 文档提取 | 2 | 规则转写的模拟条款及段号，仅冒烟 |
| 信息澄清 | 1 | 缺金额、对象、核保层级时不自行补全 |
| 无结果 | 1 | 采样时已验证指定关键词零命中 |

真实规则覆盖：高保额设备（>=500万元、011301 前导零）、费用A+A3严格大于45、都江堰健康险日期左闭右开、新津机构和代理代码、团意险高风险排除逻辑、四川非机动车多限额、遂宁700元历史方案、湖北电动车期间原始逻辑、温州学平险方案二、个代渠道限定。

每条条件及动作是数据库当前记录的保真依据，不意味着它是业务合理性或当前有效性的审核结论。湖北期间原文 `>365 或 >366` 等情况要求保留原文并提示疑点，不能静默纠错；过期规则也不应被说成当前适用。规则未标注业务状态/生效完整口径。

所有案例标为 `draft_requires_business_review`，当前统一放在 `pilot_review`，尚未划分正式开发/验收集。以 source_group 为最小划分单位，近重复规则还须按产品/模板族合并分组。同一来源的检索、展示、编写、文档不能分散到两侧。32 条案例不是 32 个独立业务来源，不能据此计算可靠泛化结论。

本轮10条源规则均只有一个动作、无否则，未覆盖多动作顺序、真实否则分支、真实长文档、跨段例外、长历史、多轮指代和取消恢复。数据库已知一条目标不等于完整相关集合，暂时不得报告完整 Recall@K。规则编写样本是已有规则规范化，不代表陌生新需求创作能力。真实文档验收必须另用业务文档及人工逐条来源标注，不能用模拟文档分数替代。

## 每项功能只保留1—2个核心质量指标

| 功能 | 核心指标及公式 | 判分要点 |
| --- | --- | --- |
| 规则检索 | **目标命中率@6**=前6条含目标的案例数/10；**MRR@6**=各例目标排名倒数的平均值，未命中计0 | 分别评工具候选与最终展示；按不同规则去重。相关全集审核后才加 Recall@6 |
| BOM映射 | **字段映射准确率**=正确对象与路径的案例/8；**类型及父链整例正确率**=类型和完整父链均正确的案例/8 | 内部工具路径用于判定，最终业务答复用中文；不能靠标签同名算正确 |
| 已有规则展示 | **关键要素准确率**=正确的已标注要素/全部已标注要素；**整例保真通过率**=全部原文条件及动作保持且无新增的案例/6 | 先人工拆标对象、值、比较符、逻辑、例外、分支和参数。关键金额错则整例失败，不用流畅度补分 |
| 规则编写 | **语义整例通过率**=条件/边界/动作全部等价的案例/4；**有据映射率**=有BOM或方法证据且类型兼容的引用数/全部引用数 | 不以关键词命中代替语义；严格检查等号、单位、前导零、AND/OR；不得假称引擎执行通过 |
| 文档提取 | **规则召回率**=正确一对一匹配标注规则数/标注规则总数；**有据精确率**=语义正确且有正确来源位置的输出规则数/输出规则总数 | 固定规则粒度，重复输出只匹配一次；无输出时精确率记0；不应提取规则的纯背景文档另评，不混零分母 |
| 澄清与无结果 | **应澄清/无结果案例通过率**=正确处理案例/适用案例；**虚构率**=出现无依据确定字段/阈值/规则的案例/适用案例 | 本版仅2例，各子类报告n=1，不能推断稳定比例；后续加入信息充足对照，评估过度澄清 |
| 运行稳定性（另建机制集） | **正常收尾率**=成功、错误、取消均正确结束且前端解除busy的任务/总任务；**权限违规执行数** | 通过mock/故障注入测取消、多轮恢复、越权和错误；本版业务集不代替现有tests回归 |

按功能宏平均，每例失败/超时计失败；另列关键错误数。不要把不同任务拼成一个总分，也不要剔除失败再算质量。自动比ID/数值仅能辅助，复杂语义由业务人员审核。每例重复3次保留逐次分数，不能选最好的一次。业务审核后另定验收门槛，本文件不擅自指定公司通过线。

## 性能评测：测三个层次

1. 工具组件：绕过模型，独立测 bom_search 和 rule_search；分开统计启动/建连首请求与同进程复用请求。既测直接核心，也测 JSONL 桥接以定位开销。
2. 模型组件：在私有模型兼容接口上，用固定输入/输出长度和推理配置采集请求首输出、完整耗时、Token用量；这是单次模型请求，不等于完整Agent任务。
3. 端到端：从评测客户端发出 `/api/prompt` 到 SSE 正文及 `agent_settled`，包含意图理解、所有模型轮次、工具和持久化。使用全新sid和隔离评测存储，多轮案例内部才复用sid；不要将压力测试写进真实用户历史。

建议优先看：**最终答案首正文时间、任务总耗时P95、失败率、满足质量和时延要求的任务吞吐**。首Token用于诊断模型，不能独自代表用户体验。

| 指标 | 精确定义/测法 |
| --- | --- |
| 模型TTFT | 单次模型HTTP请求发出→首个非空输出；分别记录 reasoning/content/tool-call 首输出类别。思考首Token和正文首Token分列 |
| 首个可见正文时间 | 客户端发送prompt前的t0→首个非空 `message_update.assistantMessageEvent.type=text_delta`。排除thinking、心跳、HTTP200、工具状态 |
| 最终答案首正文时间 | t0→最终无工具调用的助手消息的首个正文delta；按模型请求序号缓存首delta，在message_end确认消息无toolCall后回填，不能误用检索前的“正在查询” |
| 任务总耗时E2E | t0→本轮 `agent_settled`；同时区分业务成功、错误、取消。最后一段正文时间可另存，用来定位落盘/收尾开销 |
| 输出速度/TPOT | 对单次模型请求，N>1时 TPOT=(最后输出Token时间−首输出Token时间)/(N−1)。Token必须来自相同tokenizer/服务usage；推理Token与正文口径分列。不可用中文字符数冒充Token |
| 流式间隔 | 客户端相邻非空正文chunk的间隔，报P95及最大停顿。一个chunk可含多Token，SSE chunk间隔不得称作精确ITL。工具等待期间停顿单列 |
| 工具耗时 | 按toolCallId配对tool_execution_start/end；分工具报P50/P95、错误、重试次数及冷/热。核心elapsedMs不覆盖完整桥接/启动耗时 |
| 成功率及吞吐 | 成功任务数/全部发起任务；成功任务数/整个测量窗口秒数；另报质量合格且符合预定时延SLO的goodput。超时/拒绝/失败不能从分母删除 |
| 资源与调用开销 | 每任务模型请求数、工具次数、输入/输出/思考Token；CPU/RSS、GPU利用率/显存、模型排队时间（有服务器权限才采）。摘要请求也计入，拿不到usage标未采集 |
| 取消生效耗时（辅助） | 发出abort→该任务停止输出并正确settled，另用服务侧确认模型流/工具已停止。HTTP abort返回不等于取消贯通 |

当前代码已有 text_delta、thinking_delta、工具开始/结束、message_end、agent_settled 事件，但没有完整性能埋点；严格Token级性能需模型适配或服务端指标配合。SSE没有可靠补发，测量前先建立订阅并确认就绪，再发prompt；断流任务计测量失败，不能静默补算成功。API接受任务的HTTP200不算成功回答。客户端时间使用单调高精度时钟，不能混合服务器墙钟直接相减。

## 可执行的测量步骤

1. 冻结测试集哈希、规则/BOM版本、代码、模型、系统提示词和Skills、温度、最大输出、上下文长度及硬件。工具/模型/端到端分别报告；不要和mock回归混报。
2. 从本集分层取短规则、复杂规则、BOM、规范化；另补真实长文档和长历史。按真实请求的输入/输出Token长度分桶；先保证业务质量，再比较延迟。
3. 开发基线先顺序执行每例3次，看波动和故障；这只能给初步统计。正式性能每个负载条件建议至少100个完成/失败记录，P95同时给样本数，样本不足不报告P99可靠结论。
4. 冷启动单独测至少5次，使用独立测试进程重启，不清理数据库/WAL或重启现有用户服务。热启动预热后测，记录是否模型前缀缓存命中；不同候选配置保持同等缓存条件。
5. 应用并发先测1、2、4、8个不同sid，每档先预热后稳定测5分钟或至少100次，明确总请求上限；不可回收会话容量为10，超过容量的拒绝属于本机架构限制，不能只归因模型。并发会话数与模型并发不是同一概念。
6. 固定并发闭环负载用于比较，若要找饱和点，再补固定请求到达率的开环测试，记录到达率、实际吞吐、排队及超时，避免客户端等待掩盖排队。停止条件预先约定，不在真实生产数据库上无上限施压。
7. 每档报告P50/P95、成功/失败/超时/拒绝数、吞吐、逐任务质量、资源及原始记录。按冷/热、输入长度、任务类型分组；不要将不同分布平均后掩盖慢任务。模型对比使用相同输入和长度策略，记录实际输出Token。

报告建议字段：case_id/run_id/sid、负载档位、输入输出长度、t0/首可见正文/最终答案首正文/最后正文/settled、工具调用与耗时、模型请求与Token、状态/错误分类、质量判定。日志不含密钥，真实业务文本留在受控本地目录。

指标参考：[vLLM官方Metrics](https://docs.vllm.ai/en/stable/design/metrics/)、[NVIDIA推理基准概念](https://developer.nvidia.com/blog/llm-benchmarking-fundamental-concepts/)。服务端指标名称与Token/chunk统计方式随部署版本核实，不能把服务端TTFT与应用端最终答案延迟混报。

## 本轮针对性评测（2026-10-26）

用户已确认本轮按现有测试集和标注已审核通过处理；历史文件中的 draft 标记保留原始快照。新增 `python -m evals.run_authoring` 对 UW-025～030 各运行 3 次真实模型/只读工具调用（18 次，每次最多 300 秒）；仅发送 input，不发送 expected。报告输出到 private 的独立目录，失败/超时计入分母。自动交付检查率只反映格式、来源标记与成功工具调用存在性，不能替代语义整例通过率、有据映射率、规则召回率或有据精确率。性能测量从 SessionManager 提交至结束，排除 HTTP/SSE 传输，不标称网页端到端延迟，也不将状态提示当作首正文。小样本 P95 仅供诊断，无正式时延门槛。

本轮实际结果：14 项回归通过；18 次真实评测 7 次完成、11 次超时。完整质量、性能、证据缺失及测量限制见[验证报告](../docs/VALIDATION_2026-10-26.md)，不能据此宣布业务验收通过。
