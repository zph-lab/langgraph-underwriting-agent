# Agent 架构、技术与评测说明

本文说明 LangGraph Agent 的架构、MCP 检索服务及在线 API 模型评测方法。Agent 与公司已有规则文档编辑器集成运行。

## 开发与集成范围

| 范围 | 内容 | 代码入口 |
| --- | --- | --- |
| Agent 运行层 | 状态图、模型与工具循环、任务分流、交付检查 | `langgraph_app/graph.py`、`authoring.py` |
| 模型与上下文 | 流式适配、证据输入视图、预算、重复结果引用 | `langgraph_app/model.py`、`context.py` |
| 会话运行管理 | SQLite 检查点、任务取消、期限、事件订阅 | `langgraph_app/manager.py` |
| MCP 能力封装 | 标准 stdio 服务、只读工具注册、结构化结果 | `mcp_service/server.py` |
| 业务检索 | BOM 字段与方法、规则库查询 | `tools/` |
| Web 交互 | 对话、附件、SSE、会话及进度展示 | `backend/`、`web/` |
| 系统集成 | ASGI 挂载、生命周期、导航与编辑器适配 | 根目录 `merged_app.py`、`langgraph_app/editor.py` |
| 评测优化 | 数据构建、真实任务运行、证据回放和配对比较 | `evals/`、`tests/` |

表中 Agent 模块路径均相对于 `ar_agent开发/agent_1/airong_agent_test1/`。公司已有编辑器位于 `rule_editor_new/`；仓库保留该模块以支持统一运行。

## MCP 接入与当前调用方式

项目使用 MCP Python SDK 的 FastMCP 暴露两个工具：

- `bom_search`：按关键词检索 BOM 字段与方法，可指定数量、类型及是否包含方法。
- `rule_search`：在配置范围内检索已有规则，返回规则展示及结构化信息。

服务使用 stdio，由外部 MCP 客户端启动和管理。在 Agent 业务目录、已安装依赖的 Python 环境中运行：

```powershell
python -m mcp_service.server
```

## 工程设计的价值

LangGraph 将模型生成与检索组织为有状态循环；BOM 和已有规则为业务回答提供可审核依据。提示词与领域 Skills 约束四段式交付，有限交付检查可拦截缺少必要结构的答复，但不能证明业务语义全部正确。

上下文优化使用专用模型输入视图消除重复文本，保留原始检查点与工具事件；同轮重复结果用引用表示，并通过预算及检索收敛限制循环。这样既能测量输入与调用开销，也保留问题追溯所需证据。

统一工作台复用公司编辑器的既有能力。Agent 提供规则辅助生成、校验适配及工作区切换，用户负责后续审核、粘贴及上传。该集成未实现自动发布闭环。

## 在线 API 模型评测

使用相同输入、业务数据和提示词，通过 Agent 调用在线 API 模型，比较成本、速度与实际输出质量。每轮记录服务商、模型 ID / 版本、参数、代码版本和测试日期。真实评测会产生 API 费用，应在配置好服务和测试预算后执行。

### 核心指标

| 指标 | 口径 | 单位 |
| --- | --- | --- |
| 累计输入 Token | 单任务所有模型请求的输入 usage 求和，包括工具循环、摘要和修正请求 | Token |
| 累计输出 Token | 单任务所有模型请求的输出 usage 求和；服务商单列的 reasoning 用量单独保留，避免重复计数 | Token |
| 首 Token 时间 | 单次 API 请求发出至首个非空输出增量；记录输出类型，首正文时间单列 | 秒 |
| 响应时间 | 客户端提交任务至收到最终结果并确认任务结束，含检索及所有模型轮次 | 秒 |
| 转换准确率 | 语义完全正确的转换任务数 / 全部转换任务数 | % |
| 检索准确率 | 最终结果命中标注目标的检索任务数 / 全部检索任务数 | % |

转换任务逐例核对对象、字段、阈值、比较符、AND/OR、日期边界和动作参数，全部正确才计为通过。检索任务固定返回数量（例如前 6 条），以命中事先标注的目标规则或 BOM 路径为通过；该指标是任务命中率，不等同于返回条目的精确率。两种任务分别统计准确率。

API usage 未返回时标记未采集；取消或异常中断造成用量缺失时，将已收到的 Token 合计标为下界。保留提供方的原始 usage，不用中文字符数估算 Token。首 Token 时间按 API 请求逐条采集，工具调用、推理和正文分开，不能用页面“正在处理”提示代替。

### 简单执行流程

1. 准备固定的转换与检索案例，为每例标注参考答案或目标结果，参考答案不发给模型。
2. 通过 Agent 调用已配置的在线模型；每例使用独立会话，建议重复 3 次并保留全部结果。
3. 记录每次 API 请求的 usage 和首 Token 时间，同时记录客户端任务开始及结束时间。
4. 人工核对转换与检索结果。失败和超时计入相应准确率分母，不能删除后再计算。
5. 汇总累计输入 / 输出 Token、API 请求平均首 Token 时间、成功任务平均响应时间，以及两类准确率。同步列出完成、失败、超时数量。

首 Token 的平均值按 API 请求统计，响应时间按任务统计，二者不混用。可比较不同在线模型，也可比较同一模型优化前后的结果；保持输入与配置一致。若模型有随机波动，保留每次重复运行，不只选最好结果。

### 记录模板

| 案例 | 模型 | 任务类型 | 累计输入 Token | 累计输出 Token | API 平均首 Token 时间（秒） | 总响应时间（秒） | 是否准确 | 状态 |
| --- | --- | --- | ---: | ---: | ---: | ---: | --- | --- |
| 待采集 | 待配置 | 转换 / 检索 | — | — | — | — | — | 完成 / 失败 / 超时 |

模板中的首 Token 值为该任务内 API 请求的平均值；原始记录仍保留每次请求的数据。超时任务填观察时长及超时状态，不填为正常完成耗时。

### P95、P99 是否需要

P95 表示 95% 的记录耗时不超过该值，P99 表示 99% 的记录耗时不超过该值。例如响应时间 P95 为 10 秒，表示约 95% 的请求在 10 秒内完成，其余约 5% 更慢。它们用于识别平均值掩盖的慢请求，不是准确率指标，也不是在线模型评测的必选项。

当前阶段先采用逐例记录、平均时间、准确率和失败 / 超时数量即可。后续需要评估并发、服务稳定性或约定响应时限时，再加入 P95；P99 对样本量更敏感，待积累更充分的请求记录后使用。计算时附样本量和失败 / 超时口径，避免仅统计成功请求而掩盖问题。

## 历史结果与新评测

历史 UW-025 配对中，累计输入 Token 从 118,431 降至 68,308，运行层任务耗时从 254.58 秒降至 226.31 秒；每组仅一次，不外推整体效果。历史报告中的耗时不包含 HTTP/SSE 与浏览器传输，不能与新方案客户端总响应时间直接混算。

新的在线 API 评测应同时采集累计输出 Token、API 首 Token 时间、客户端总响应时间和转换 / 检索准确率。目前尚未按这一完整口径重新执行，未采集的项目不填写成绩。
